# Migration compatibility checks for the next storage schema version (#392)

[upgrade-migrations.md](upgrade-migrations.md) sets the rules: additive
storage changes keep `SCHEMA_VERSION`, while breaking changes bump it and
migrate in-flight state inside a governance-gated migration window. Two
existing checks enforce parts of this:

- `storage_keys.json` (#159) fails `nbbs-tests` on **any** `DataKey` drift.
  It cannot say whether the drift is safe.
- The release gate (#473) checks that the **deployed** version matches the
  API's version.

Neither check answers: *is the layout on this branch a valid next version,
compared with what is deployed?* This check answers that, before merge.

```bash
cd api
npm run migration:storage-compat           # human-readable, exit 0/1/2
npm run migration:storage-compat -- --json
npx jest src/migrations                    # also runs in CI's `npm run test`
```

Admin API: `GET /api/v1/migrations/storage-schema/compatibility`
(`JwtAuthGuard` + `AdminGuard`, read-only).

## Inputs

| File | Role |
|------|------|
| `contracts/tests/fixtures/storage_keys.v1.json` | **Frozen baseline**: the storage layout schema version 1 shipped with. Its digest is pinned in the spec, so it can never be edited. |
| `contracts/tests/fixtures/storage_keys.json` | **Candidate**: the layout on this branch, regenerated by the existing fixture flow. |
| `contracts/tests/fixtures/schema_migrations/v2.json` | **Plan** for the next version. Starts as an empty `draft`. |
| `contracts/*/src/lib.rs` `SCHEMA_VERSION` | Per-contract version on this branch |
| `contracts/shared/src/lib.rs` `CURRENT_SCHEMA_VERSION` | Suite version |

The baseline is the newest frozen `storage_keys.v<N>.json` with `N` ≤ the
suite version. While a bump to `N+1` is in progress, `v<N>` remains the
baseline.

## Rules

A change to a key is **added** (a new constructor), **removed**, or
**changed** (same constructor, different XDR). Removed and changed keys are
**breaking**.

| Code | Rule |
|------|------|
| `BREAKING_CHANGE_WITHOUT_VERSION_BUMP` | A contract with breaking changes must bump `SCHEMA_VERSION` to `N+1` |
| `VERSION_SKIP` / `VERSION_REGRESSION` | Versions move one at a time and never go back |
| `SUITE_VERSION_MISMATCH` | Every contract's version equals `CURRENT_SCHEMA_VERSION` (the suite moves together, as `nbbs-tests` already asserts) |
| `UNPLANNED_BREAKING_CHANGE` | Every removed or changed key has a plan step |
| `PLAN_NOT_READY` | A plan backing breaking changes is `"status": "ready"` (reviewed), not `draft` |
| `PLAN_INVALID` / `PLAN_VERSION_MISMATCH` | The plan parses and migrates `N → N+1` |
| `MISSING_ROLLBACK` | A breaking plan documents its rollback path |
| `STALE_PLAN_STEP` | Steps name real baseline keys |
| `REWRITE_TARGET_MISSING` | `rewrite.to` is a candidate key. A re-encoded key must be rewritten, not retired. |
| `IN_FLIGHT_STATE_RETIRED` | Investor or protocol state (balances, escrow, unclaimed coupons, orders, reports, proposals) is never retired |
| `MIGRATION_WINDOW_REQUIRED` | Rewriting in-flight state happens inside `begin_migration` / `finalize_migration` |
| `NON_IDEMPOTENT_STEP` | Every step is idempotent, so a partially applied migration can be **retried** |
| `NON_RESUMABLE_STEP` | Rewrites of keyed families (`HolderBalance(…)`) run in cursor batches, so a retry resumes rather than restarts |
| `UNGATED_STEP` | Every step executes through the governance timelock (**authorization**) |

Warnings (non-blocking): `VERSION_BUMP_WITHOUT_BREAKING_CHANGE` (allowed for
interface-only bumps) and `PLANNED_STEP_WITHOUT_CHANGE`.

In-flight key families are listed in `IN_FLIGHT_STATE_KEYS` in
`api/src/migrations/storage-schema-compat.ts`. Extend that list when a new
`DataKey` holds user or protocol state.

## Workflow for a breaking change in v2

1. Change the `DataKey` enum and regenerate the candidate fixture:
   `cargo test -p nbbs-storage --features storage-fixture-update regenerate_storage_fixture_file`.
2. Bump `SCHEMA_VERSION` in each contract and `CURRENT_SCHEMA_VERSION` to `2`.
3. Add a step to `schema_migrations/v2.json`, for example:
   ```json
   {
     "contract": "bond-issuer",
     "key": "HolderBalance(1, addr)",
     "action": "rewrite",
     "to": "HolderBalanceV2(1, addr)",
     "description": "Copy balances to the v2 key with checkpoint metadata; v1 key kept until finalize.",
     "idempotent": true,
     "resumable": true,
     "governanceGated": true,
     "migrationWindow": true
   }
   ```
4. Run `npm run migration:storage-compat` and fix every `[FAIL]`.
5. After review, set `"status": "ready"`.
6. When v2 is **deployed**, freeze the candidate as `storage_keys.v2.json` and
   pin its digest in `storage-schema-compat.spec.ts`. That file is now the
   baseline for v3. Start `schema_migrations/v3.json` as an empty draft.

## Operational edge cases and recovery

- **The check fails on a branch you did not expect to be breaking.** A
  `changed` entry means the XDR of an existing key moved. This usually comes
  from reordering enum variants or changing a payload type. Prefer reverting
  that over planning a migration.
- **Partial migration on-chain.** Steps are required to be idempotent and
  resumable, so the recovery is to **re-run the same step**. It skips entries
  already written and continues from its cursor. If the cutover has to be
  abandoned, `rollback_migration` re-verifies the pre-cutover snapshot
  (upgrade-migrations.md §5). v1 keys are kept until `finalize_migration`, so
  re-executing the pinned v1 WASM reads unchanged state.
- **Plan merged as `ready` but the upgrade is postponed.** Leave it. The plan
  describes the candidate. If the layout changes again, the check fails until
  the plan is updated.
- **Inputs missing in a deployed API** (fixtures are not shipped). The admin
  endpoint answers `503` and never reports "compatible". The CLI exits `2`.
- **Baseline edited by mistake.** The pinned-digest test fails. Restore the
  file from git. Never re-pin a digest for an already-shipped version.

## Migration plan for this change

This change is purely additive and preserves every existing contract.
`storage_keys.v1.json` is a byte-for-byte copy of the current
`storage_keys.json`, the v2 plan is an empty draft, and no `DataKey`, version
or API response changes. The current repository reports `COMPATIBLE`, with all
seven contracts `identical`.
